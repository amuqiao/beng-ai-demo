# 输油泵智能运维助手 demo 演示方案 v2

> 一句话主旨：用长岭站 P-1 输油泵机组“疑似不对中”的一次关注级诊断事件，演示 AI 如何把异常发现、专业诊断、专家复核、知识命中、处置建议、票卡报告生成和案例复用串成一个可讲清楚的业务闭环。
>
> Demo 定位：面向业务方、评委/领导、演示主持人和 demo 制作人员的演示方案，不是开发基准文档，也不是生产系统建设方案。
>
> 主故事：第一次，P-1 出现疑似不对中异常，系统辅助完成诊断与处置闭环；第二次，同类相似异常出现，系统命中第一次沉淀的经验并给出复用建议。

本文中的 Agent 指“智能助手自动整理材料的能力”：基于已确认的诊断结论和知识依据，辅助生成建议、票卡草稿、报告草稿和复用说明。

## 1. 业务痛点

输油泵是管网运行中的关键动设备，运维质量直接影响安全、稳定和成本。申报材料里提到的现状可以压缩成四个演示需要回应的问题：

| 业务痛点 | 现场常见表现 | demo 要回应的问题 |
| --- | --- | --- |
| 异常发现不够早、不够聚焦 | 运行数据、检测报告、趋势曲线分散，异常从“看见数据”到“进入诊断”需要人工判断 | 系统能不能把一次异常清楚地标记为关注级诊断事件 |
| 诊断依据不够透明 | 只看到结论容易被认为是“黑盒判断” | 系统能不能说明为什么判断为疑似不对中 |
| 处置依赖专家经验 | 作业卡、历史案例、报告模板分散，专家经验难以快速复用 | 系统能不能命中知识库并辅助形成处置建议 |
| 经验沉淀不足 | 维修报告归档后，下次相似异常仍要重新翻材料 | 系统能不能把第一次闭环沉淀成下一次可命中的案例 |

首版 demo 不追求覆盖所有输油泵运维场景，而是先把一条最能说明价值的闭环讲透：

```text
从被动看数据
  到
发现异常、解释依据、专家把关、形成处置、生成材料、沉淀复用。
```

## 2. Demo 要证明什么

本 demo 证明的不是“系统已经替代人工完成生产运维”，而是证明一条智能运维闭环在业务上讲得通、演得完、边界清楚。

| 要证明的事 | 演示中的表达方式 | 不能说成什么 |
| --- | --- | --- |
| 异常能被识别 | 长岭站 P-1 被标记为关注级诊断事件，进入专业诊断流程 | 不说成实时生产报警 |
| 诊断有证据 | 演示中呈现“疑似不对中”的专业诊断结论，并展示二倍频、相位差、多测点振动、基础振动偏大等依据 | 不说成模型自动定责或真实生产推理 |
| 专家仍是关键角色 | 专业诊断结论进入专家复核，专家确认后才进入处置建议环节 | 不说成 AI 自动替代专家 |
| 知识能支撑处置 | 知识库命中对中作业卡标准模板、诊断报告、历史案例和专家经验规则 | 不说成开放式万能问答 |
| Agent 能整理材料 | Agent 生成处置建议、处置票卡草稿、维修报告草稿和复用说明 | 不说成真实派工审批 |
| 经验能复用 | 第二次相似异常命中第一次 P-1 案例，推荐相似处置经验 | 不说成全类型故障自动覆盖 |

一句演示总口径：

```text
模型判断“可能是什么问题”，
知识库说明“为什么这样处置”，
Agent 整理“怎么处置、怎么成文、怎么复用”，
专家和业务人员确认“是否采纳、是否闭环”。
```

## 3. 首次异常闭环

首次闭环是整场 demo 的主线，建议只围绕“长岭站 P-1 输油泵机组疑似不对中”展开，不再引入轴承故障、松动、汽蚀等其他故障分支。

### 3.1 主线流程

```text
长岭站 P-1 设备主页
  -> 检测报告导入 / 趋势回放
  -> 标记关注级诊断事件
  -> 呈现专业诊断结论：疑似不对中
  -> 展示诊断依据
  -> 专家复核确认进入处置建议
  -> 知识库命中对中作业卡标准模板、诊断报告、历史案例、专家经验规则
  -> Agent 生成处置建议和处置票卡草稿
  -> 现场按对中模板执行检查 / 调整
  -> 复测指标回落或验收通过
  -> 人工确认闭环成立
  -> Agent 生成维修报告草稿
  -> 沉淀为 P-1 疑似不对中处置案例
```

### 3.2 关键讲点

| 演示节点 | 主持人要讲清楚什么 | 画面上要支撑什么 |
| --- | --- | --- |
| 异常起点 | “我们从长岭站 P-1 的检测报告和趋势回放进入，这里不是严重故障报警，而是关注级诊断事件。” | 设备名、站场名、状态等级、异常趋势、异常测点 |
| 专业诊断 | “演示中呈现的是疑似不对中的专业诊断结论，并展示证据，不是凭空生成结论。” | 疑似不对中、风险等级关注、二倍频、相位差、多测点振动等依据 |
| 专家复核 | “专业诊断结论先给专家看，专家确认后才进入处置建议。” | 复核意见、确认状态、进入处置的触发动作 |
| 知识命中 | “知识库命中的是能支撑处置的业务材料，包括作业卡、诊断报告、历史案例和专家规则。” | 命中材料列表、引用依据、对中作业卡标准模板 |
| Agent 辅助 | “Agent 不替人审批，只把已确认的结论和知识依据整理成建议、票卡和报告草稿。” | 处置建议、票卡草稿、维修报告草稿 |
| 闭环判定 | “现场按对中模板完成检查或调整后，复测指标回落并由人员确认，才算本次闭环成立。” | 执行状态、复测结果、验收结论、确认人 |
| 闭环沉淀 | “处置反馈、复测结果和报告结论会沉淀成案例，服务下一次相似异常。” | 处置结果、复测结果、案例标签、入库状态 |

### 3.3 P-1 案例口径

| 要素 | 建议演示口径 |
| --- | --- |
| 设备 | 长岭站 P-1 输油泵机组 |
| 事件性质 | 关注级诊断事件 |
| 诊断结论 | 疑似不对中 |
| 风险表达 | 关注，不表达为严重故障 |
| 诊断依据 | 二倍频成分、相位差、多测点振动、基础振动偏大 |
| 知识命中 | 对中作业卡标准模板、相关诊断报告、历史案例、专家经验规则 |
| Agent 输出 | 处置建议、处置票卡草稿、维修报告草稿 |
| 人工把关 | 专家复核诊断结论，业务人员确认处置、复测结果和闭环状态 |
| 结果沉淀 | P-1 疑似不对中处置案例，带复用标签 |

对中作业卡建议讲成“标准模板卡，需业务确认是否适配 P-1”，不要讲成已经完成 P-1 生产作业审批的正式票卡。

首次闭环成立要有三个证据，不满足就不能讲成“案例已完成闭环”：

| 闭环证据 | 演示中怎么讲 |
| --- | --- |
| 处置执行成立 | 现场按对中作业卡模板完成检查或调整，记录执行人和执行结果 |
| 复测验收成立 | 处置后振动等关键指标回落，或达到业务方确认的验收口径 |
| 人工确认成立 | 专家或授权业务人员确认本次处置可关闭，报告草稿才能作为案例沉淀依据 |

## 4. 第二次相似异常复用

第二次复用是 demo 的价值收束：证明第一次闭环不是停在报告归档，而是形成可再次命中的经验。

### 4.1 复用流程

```text
第二台同类设备出现相似症状
  -> 再次识别为关注级诊断事件
  -> 呈现专业诊断结论：疑似不对中
  -> 知识库命中第一次 P-1 处置案例
  -> 展示命中的案例标题、相似依据、复用内容和第一次闭环结果
  -> 推荐相似处置经验和对中作业卡标准模板
  -> Agent 生成复用说明
  -> 提示仍需专家复核和现场安全确认
```

### 4.2 复用讲法

主持人可以这样收束：

```text
第一次异常，系统帮助我们把诊断、处置和报告做成闭环；
第二次相似异常，系统不只是重新生成一段建议，
而是命中了第一次沉淀的 P-1 案例，
把相似症状、处置经验、作业卡模板和复测要求一起推荐出来。
```

复用页面要讲清楚三件事：

| 要讲清楚的事 | 建议表达 |
| --- | --- |
| 为什么相似 | 同样出现二倍频、相位差、多测点振动、基础振动偏大等症状标签 |
| 复用了什么 | P-1 疑似不对中处置案例、对中作业卡标准模板、复测验收要求 |
| 谁来决定是否采纳 | 仍由专家复核和现场人员确认，不由系统自动决定 |

复用页必须把“这不是普通检索”讲出来，建议固定展示四个元素：

| 复用元素 | 页面上应出现什么 |
| --- | --- |
| 命中的案例 | 案例标题或编号，例如“P-1 疑似不对中处置案例” |
| 相似依据 | 本次异常与 P-1 案例匹配的症状标签和设备范围 |
| 复用内容 | 沿用第一次案例中的处置步骤、复测要求、报告结构和注意事项 |
| 闭环关联 | 显示第一次案例已完成复测验收和人工确认，本次建议来自已闭环经验 |

## 5. 页面与讲解顺序

页面不宜做成完整设备管理平台，首版控制在 5 个演示页以内，每页只承担一个清晰讲点。

| 顺序 | 页面 | 主持讲解重点 | 证明什么 |
| --- | --- | --- | --- |
| 1 | 设备总览与诊断事件页 | 从长岭站 P-1 进入，展示设备状态、趋势曲线、异常测点和关注级诊断事件 | 异常起点可信 |
| 2 | 专业诊断与专家复核页 | 展示疑似不对中、风险关注、诊断依据，以及专家复核入口 | 诊断有证据，责任有边界 |
| 3 | 知识命中与处置建议页 | 展示命中的作业卡、诊断报告、历史案例和专家经验规则，Agent 形成处置建议 | 建议有依据，不是凭空生成 |
| 4 | 处置票卡与维修报告页 | 用步骤条区分“草稿生成前 -> 现场执行后 -> 复测完成后”，再展示报告草稿 | 预警能走向可判定的闭环材料 |
| 5 | 案例复用页 | 展示 P-1 案例入库标签、闭环结果，以及第二次相似异常命中的复用证据 | 经验能服务下一次异常 |

推荐讲解节奏：

```text
第一段：业务为什么需要它
第二段：P-1 第一次异常如何闭环
第三段：第二次相似异常如何复用
第四段：边界说明和定稿口径
```

如果演示时间较短，可以压缩为一句话串联：

```text
我们先看 P-1 怎么从关注级异常走到专家复核和处置报告，再看这次经验怎样在第二次相似异常中被命中复用。
```

## 6. 素材与确认项

### 6.1 当前素材状态

这里区分“方案逻辑已成立”和“素材已确认”。现有材料可以支撑演示主线设计，但涉及真实数据、报告样张和现场反馈时，仍需要业务方确认或标注为演示模拟材料。

| 内容 | 当前状态 | 使用方式 |
| --- | --- | --- |
| P-1 疑似不对中主线 | 方案逻辑已成立 | 作为首版唯一主故事，需业务确认口径 |
| 关注级诊断事件口径 | 方案逻辑已成立 | 作为异常起点，不夸大为严重报警 |
| 诊断依据 | 方案逻辑已成立 | 用二倍频、相位差、多测点振动、基础振动偏大解释结论 |
| 知识库最小集合 | 待业务确认素材版本 | 命中诊断报告、作业卡模板、历史案例、专家经验规则 |
| Agent 输出范围 | 方案逻辑已成立 | 生成处置建议、票卡草稿、维修报告草稿、复用说明 |
| 第二次复用 | 待业务确认样例来源 | 可用真实 / 脱敏样例；如使用演示模拟样例，讲解和画面必须标注 |

### 6.2 建议业务方确认或补充

| 确认项 | 为什么需要确认 | 默认处理方式 |
| --- | --- | --- |
| P-1 是否作为首版唯一主线 | 避免演示发散 | 默认选长岭站 P-1 |
| “疑似不对中”口径是否认可 | 保证诊断结论可讲、不过度 | 默认按疑似结论展示 |
| 风险等级是否按“关注”展示 | 避免把 demo 讲成严重事故 | 默认按关注级诊断事件展示 |
| 谁有资格做专家复核和现场确认 | 避免演示时被追问责任边界 | 需业务方指定角色口径 |
| 复测验收标准是什么 | 决定什么条件下可以讲成闭环完成 | 需业务方确认复测指标或验收描述 |
| 对中作业卡是否适配 P-1 | 避免把标准模板误讲成正式适配文件 | 默认讲成标准模板卡，待业务确认适配 |
| 维修报告模板是否可用 | 支撑报告草稿的业务格式 | 优先使用真实或脱敏样张；演示模板必须标注 |
| 第二次相似异常样例来源 | 支撑复用页面，并避免被理解为真实历史事件 | 优先使用真实或脱敏样例；演示模拟样例必须在画面和讲解中标注 |
| 真实或脱敏趋势数据 | 提升现场感 | 优先使用真实或脱敏数据；演示样例数据必须标注 |
| 现场处置反馈记录 | 支撑复测和闭环 | 优先使用真实或脱敏记录；演示记录必须标注并经业务确认 |

### 6.3 素材优先级

```text
必须确认：
  P-1 主线、疑似不对中、关注级诊断事件、专家复核角色、现场确认角色、复测验收口径、作业卡模板口径。

强烈建议补充：
  趋势曲线样例、诊断报告样张、维修报告模板、现场处置反馈。

可以使用演示模拟材料，但必须标注：
  第二次相似异常样例、复用说明、票卡草稿内容。
```

## 7. 首版边界

首版 demo 要主动说清边界，避免评委或业务方误解为生产系统已经建成。

| 边界 | 推荐说明 |
| --- | --- |
| 不演生产系统接入 | 使用演示数据和预置事件把闭环讲清楚 |
| 不演真实模型训练 | 展示诊断结论和依据解释，不展示训练过程 |
| 不演 AI 自动替代专家 | 演示中呈现疑似结论，专家复核后才进入处置 |
| 不演真实派工审批 | 只展示处置票卡草稿和人工确认状态 |
| 不演全类型故障库 | 首版只围绕疑似不对中 |
| 不演全设备资产管理 | 只展示 P-1 和第二次复用所需的同类设备样例 |
| 不演开放式通用 Agent | Agent 只围绕本次异常、知识依据、票卡报告和复用说明工作 |
| 不演完整知识图谱 | 只展示知识命中和复用标签，服务演示主线 |

这不是削弱 demo，而是让首版更聚焦：

```text
先把一条闭环讲可信，
再讨论后续是否扩展到更多设备、更多故障和更多系统协同。
```

## 8. 推荐定稿口径

### 8.1 这个 demo 演什么

```text
演示 AI 如何嵌入输油泵智能运维流程：
从长岭站 P-1 输油泵机组关注级诊断事件出发，
呈现疑似不对中的专业诊断结论，
通过专家复核和知识库命中形成处置建议，
由 Agent 生成处置票卡草稿和维修报告草稿，
再把处置结果沉淀为案例，
用于第二次相似异常复用。
```

### 8.2 这个 demo 不演什么

```text
不演生产系统接入，
不演全量故障诊断，
不演模型训练过程，
不演真实派工审批，
不演模型自动替代专家判断，
不演开放式通用 Agent。
```

### 8.3 业务方现在只需要确认什么

```text
是否接受长岭站 P-1 疑似不对中作为首版主线；
是否接受“首次闭环 + 第二次复用”的两段演示；
是否认可关注级诊断事件、疑似不对中和专家复核口径；
是否认可对中作业卡作为标准模板卡参与知识命中；
是否可以提供或确认趋势数据、诊断报告、维修报告模板和现场处置反馈。
```

### 8.4 一句话收口

```text
这次 demo 不证明生产系统已经全部建成，
而是证明“输油泵智能运维助手”能围绕一台泵、一次异常、一次处置和一次复用，
把业务价值稳定、清楚、克制地讲出来。
```
