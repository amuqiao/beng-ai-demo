# 输油泵智能运维助手 demo 技术实施定版方案

本文是输油泵智能运维助手 demo 的当前技术实施口径，用于开发落地、工程拆分、验收边界和后续扩展评估。

本文不做多技术栈比较，也不承诺真实系统集成。首版技术目标是用固定结构化演示数据跑通 P-1 疑似不对中闭环和 P-2 相似异常复用验证。

## 0. 定版结论

首版固定采用 `结构化数据驱动的可交互演示 PoC`。

```text
本地结构化 demo 数据
  + 设备和测点模型
  + 趋势 / 频谱 / 相位证据
  + 预置诊断输出
  + 可视化知识命中
  + 演示态处置票卡
  + 报告模板
  + 案例入库和复用验证
```

首版目标：

```text
用同一份冻结演示数据，
跑通设备异常、诊断证据、专家复核、知识命中、处置票卡、
现场反馈、报告生成、案例入库和第二台相似异常复用这一条闭环。
```

技术原则：

1. 结构化演示数据是首版运行时真相源；业务素材只作为抽取依据。
2. 页面不直接读取 Word、Excel、图片或报告原文。
3. 诊断节点首版使用预置输出和可解释证据链，不训练真实模型。
4. 知识库首版使用可视化命中结果，不接真实向量库或真实 RAG。
5. Agent 输出限定在处置建议、票卡草稿、报告草稿和复用说明。
6. 所有派生结果必须能追溯到事件、证据、知识命中、票卡或反馈对象。
7. 前端可展示状态变化，但业务关键派生结果不要散落在页面局部常量里。
8. 不宣称真实 IMS / PI / HSE / PPS / 供应链接口已接入。
9. 不引入和首版演示无关的登录、权限、审批、消息队列或微服务复杂度。
10. 所有模块都服务于“异常发现、诊断解释、专家把关、标准处置、报告沉淀、复用验证”的主线。

## 2. 业务主线到技术模块

首版业务骨架：

```text
P-1 异常事件
  -> 诊断证据
  -> 专家复核
  -> 知识命中
  -> 处置票卡
  -> 现场反馈
  -> 报告生成
  -> 案例入库
  -> P-2 复用验证
```

技术实现按这条主线拆成 8 个模块：

| 业务节点 | 技术模块 | 主要职责 |
| --- | --- | --- |
| P-1 异常事件 | 设备与事件模块 | 加载设备、一泵一档、测点、异常事件和流程状态。 |
| 诊断证据 | 证据展示模块 | 展示趋势、阈值、频谱、相位和证据标签。 |
| 专家复核 | 复核状态模块 | 管理诊断确认、驳回、意见和进入处置的演示状态。 |
| 知识命中 | 知识命中模块 | 根据诊断输出展示作业卡、专家规则、历史案例和报告模板命中。 |
| 处置票卡 | 票卡模块 | 生成演示态处置票卡，展示角色、许可、工具、步骤。 |
| 现场反馈 | 反馈模块 | 记录调整、复测、验收和人工确认。 |
| 报告生成 | 报告模块 | 汇总事件、证据、处置和反馈，生成维修报告草稿。 |
| P-2 复用验证 | 案例复用模块 | 确认 P-1 案例入库后，让 P-2 命中该案例并展示复用理由。 |

## 3. 数据与状态边界

### 3.1 运行时真相源

运行时数据来自一个冻结的 demo 数据包。顶层集合、字段、状态和 `runtime_source` / `basis_source` 解释只维护在 [../../v1/demo-研发基准/05-结构化数据契约.md](../../v1/demo-研发基准/05-结构化数据契约.md)。

本文只固定技术原则：页面和服务读取同一份结构化数据包，业务素材只作为字段抽取依据，不作为运行时输入。

### 3.2 状态流转

首版至少支持以下演示状态：

```text
warning
  -> diagnosis
  -> review
  -> knowledge
  -> work_order
  -> feedback
  -> report
  -> case_entry
  -> reuse
```

状态只在 demo 模块内流转，不写回真实生产系统。

## 4. 前端实施口径

首版页面固定 5 个：

页面名称和顺序的唯一维护入口是 [演示路线与页面交互方案](输油泵智能运维助手-demo-演示路线与页面交互方案.md)。技术侧只按页面职责拆模块：

| 页面职责 | 主要模块 |
| --- | --- |
| 异常入口 | 设备卡、事件卡、一泵一档、测点示意、流程时间线。 |
| 诊断解释 | 趋势图、阈值线、频谱卡、相位卡、诊断结果卡。 |
| 复核和知识依据 | 复核面板、知识命中列表、命中理由、Agent 建议摘要。 |
| 处置和复测 | 处置步骤条、票卡草稿、现场反馈、复测对比。 |
| 报告和复用 | 报告预览、知识审核、案例入库、P-2 复用验证、命中理由。 |

前端职责：

```text
展示结构化数据
呈现流程状态
触发演示态确认动作
展示图表、标签、卡片和报告预览
不在页面局部重复实现核心诊断逻辑
```

如果首版先做静态原型，可以用本地 JSON 和前端状态完成；如果进入后端联调，再把同一数据契约迁移到 API。

## 5. 后端 / 服务实施口径

首版不强制必须先接后端。如果进入后端实现，建议服务边界按业务模块划分：

| 服务模块 | 职责 |
| --- | --- |
| demo data service | 读取冻结演示数据包，提供设备、事件、证据、知识、票卡、报告和复用对象。 |
| diagnosis service | 返回预置诊断输出和证据解释，不训练真实模型。 |
| knowledge service | 返回知识命中结果和命中理由，不接真实 RAG。 |
| workflow service | 管理演示态确认动作和节点状态。 |
| report service | 基于报告模板汇总报告草稿。 |
| reuse service | 在案例入库后返回 P-2 命中 P-1 案例的复用结果。 |

API 合同应围绕页面需要设计，不要暴露业务素材文件读取入口。

## 6. 规则计算

首版推荐的规则边界：

| 规则 | 首版处理 |
| --- | --- |
| 趋势进入关注区 | 可用预置事件，也可按阈值做轻量计算。 |
| 疑似不对中诊断 | 预置诊断输出，页面展示证据链。 |
| 知识命中 | 预置命中结果和命中理由。 |
| 票卡生成 | 从对中作业卡知识项复制角色、许可、工具、步骤。 |
| 报告生成 | 从事件、诊断、票卡、反馈和案例标签汇总模板段落。 |
| 复用命中 | 根据 P-2 证据标签命中 P-1 案例，展示相似理由。 |

不要在首版里加入不可解释的随机推荐、开放式生成或 silent fallback。缺少数据时应标注“业务待补”或“演示构造”，不要静默吞掉。

## 7. 报告生成

报告草稿不是模型凭空生成，而是从闭环对象汇总。

| 报告段落 | 数据来源 |
| --- | --- |
| 事件概况 | `warning_events` |
| 设备基本信息 | `assets`、`measurement_points` |
| 异常数据与诊断依据 | `telemetry_series`、`spectrum_features`、`phase_features`、`diagnosis_runs` |
| 专家复核 | `diagnosis_runs.confirmation` |
| 处置过程 | `work_orders` |
| 复测与验收 | `field_feedback` |
| 经验总结与复用标签 | `case_entries` |

报告确认后才允许提交知识入库；知识审核通过并写入 `case_entries.confirmation` 后，才允许 P-2 复用验证命中 P-1 案例。

## 8. 可枚举支线

可枚举支线是增强项，不改变首版主架构。

| 领域 | 主线 | 可枚举支线 |
| --- | --- | --- |
| 数据导入 | 本地结构化 demo 数据 | 增加 CSV 导入趋势曲线。 |
| 诊断能力 | 预置诊断输出 + 证据链 | 接入规则引擎或传统异常检测算法。 |
| 知识库 | 可视化命中卡 | 接入真实 RAG 或向量库。 |
| 报告输出 | 页面报告预览 | 导出 Markdown / PDF / Word。 |
| 系统集成 | 不接真实接口 | 试点阶段接 IMS / PI / HSE / 供应链。 |
| 故障类型 | P-1 疑似不对中 | 增加轴承磨损、不平衡、泄漏、启泵失败。 |

支线进入开发前必须单独确认数据、接口、部署和验收边界。

## 9. 不做项

首版不做这些能力：

| 不做项 | 原因 |
| --- | --- |
| 不接真实 IMS / PI / HSE / PPS / 供应链接口 | 避免演示 PoC 变成系统集成项目。 |
| 不训练真实诊断模型 | 需要样本、标签、评测和专家确认。 |
| 不接真实大模型或真实 RAG | 输出稳定性和验收边界不可控。 |
| 不本地部署大模型或多模态模型 | 需要 GPU、运维和合规投入。 |
| 不做登录、权限、审批和审计 | 首版是演示 PoC，不进入生产访问控制。 |
| 不做真实派工、HSE 办票、供应链采购 | 涉及生产责任和跨系统联动。 |
| 不做完整微服务、消息队列、异步任务 | 首版没有分布式可靠性需求。 |
| 不做全类型故障库 | 首版只围绕 P-1 疑似不对中。 |

## 10. 目录结构建议

如果进入原型开发，建议保持数据、页面和素材边界清楚：

```text
poc/
  pump-demo/
    index.html
    styles.css
    scripts/
      app.js
      data.js
    data/
      demo.json
      README.md
    assets/
      images/
      reports/
```

如果进入后端实现，再按现有工程骨架建立 API 和数据模块，不要让前端原型目录承担生产服务职责。

## 11. 验收标准

| 验收项 | 标准 |
| --- | --- |
| 数据一致 | 5 页读取同一份结构化演示数据。 |
| 主线完整 | 能从 P-1 异常事件走到 P-2 复用验证。 |
| 证据可解释 | 趋势、阈值、频谱、相位与诊断结论能对应。 |
| 人工边界 | 专家复核、处置确认、报告确认、知识审核状态清楚。 |
| 知识命中 | 作业卡、专家规则、历史案例、报告模板有命中理由。 |
| 报告可追溯 | 报告段落能对应事件、诊断、票卡和反馈对象。 |
| 知识审核明确 | P-1 案例进入可复用状态前必须有知识审核确认。 |
| 复用成立 | P-2 在 P-1 案例审核通过后命中该案例，并展示相似证据标签。 |
| 边界清楚 | 页面和话术不宣称真实系统接入、真实模型训练或专家替代。 |
