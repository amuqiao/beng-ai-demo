# 输油泵智能运维助手 demo 开发指导

本文是输油泵智能运维助手 demo 的当前开发执行指导，用于开发前准备、数据加工、页面开发、联调走查和交付验证。

它不负责对外业务口径；对外方案见 [输油泵智能运维助手-demo-AI赋能演示定稿方案](输油泵智能运维助手-demo-AI赋能演示定稿方案.md)。

## 1. 我对开发目标的理解

首版开发不是做完整输油泵生产系统，而是做一个可交互、可讲解、可验证的演示闭环：

```text
P-1 关注级异常
  -> 疑似不对中诊断
  -> 专家复核
  -> 知识命中
  -> 处置票卡
  -> 现场反馈
  -> 报告生成
  -> 案例入库
  -> P-2 相似异常复用
```

开发时要避免两个错误方向：

| 错误方向 | 为什么不做 |
| --- | --- |
| 做成巡检换皮 | 泵课题的价值在专业诊断、处置闭环和案例复用，不在多区域表单质检。 |
| 做成大而全平台 | 首版会发散到巡检、保养、项修、大修、HSE、供应链，演示主线失焦。 |

## 2. 开发心智模型

正确的数据关系：

```text
业务素材
  -> 抽取设备、测点、阈值、趋势、频谱、相位、作业卡、报告模板、知识条目
  -> 构造结构化 demo 数据包
  -> 页面运行时只读取结构化 demo 数据包
```

不要让页面运行时直接读取业务素材文件：

```text
Word / Excel / 图片 / 报告原文
  -> 现场上传
  -> 模型直接读文件
```

这条路径不进入首版。

## 3. 首版交付物

| 交付物 | 最小标准 |
| --- | --- |
| 可运行原型 | 能按 5 页路线走完主线。 |
| demo 数据包 | 覆盖设备、测点、事件、诊断、知识、票卡、反馈、报告、案例、复用。 |
| 页面交互 | 专家确认、票卡生成、反馈确认、报告入库、P-2 复用能改变状态。 |
| 演示脚本 | 主持人能按固定路线讲完，不需要临场解释数据来源。 |
| 验证记录 | 链接、页面、数据加载、主线状态和边界文案通过检查。 |

## 4. 页面开发顺序

建议按业务闭环顺序开发，不要先做大屏装饰。

页面名称和顺序只维护在 [输油泵智能运维助手-demo-演示路线与页面交互方案.md](输油泵智能运维助手-demo-演示路线与页面交互方案.md)。本文按开发阶段引用当前页面职责，不作为页面清单事实源。

### 阶段 1：数据包和页面壳

目标：

```text
创建统一 demo 数据包
搭好 5 页导航
每页展示标题、当前事件、当前节点
```

完成标准：

| 项 | 标准 |
| --- | --- |
| 数据包 | 至少包含 P-1、P-2、P-1 事件、P-1 诊断、P-1 知识命中。 |
| 导航 | 能在 5 页之间切换。 |
| 状态 | 当前节点能从 warning 走到 reuse。 |

### 阶段 2：设备和证据链

目标：

```text
让 P-1 异常起点可信，
让疑似不对中诊断有可见证据。
```

页面：

| 页面 | 必做内容 |
| --- | --- |
| 主事件入口职责 | P-1 主事件卡、一泵一档、异常测点、关注级事件。 |
| 诊断解释职责 | 趋势、阈值、频谱、相位、诊断结果卡。 |

完成标准：

```text
观众能看出 P-1 为什么被关注，
也能看出疑似不对中结论由哪些证据支撑。
```

### 阶段 3：复核、知识和处置

目标：

```text
把诊断建议推进到专家确认和标准处置。
```

页面：

| 页面 | 必做内容 |
| --- | --- |
| 复核和知识依据职责 | 复核状态、作业卡、专家规则、历史案例、报告模板。 |
| 处置和复测职责 | 处置票卡、步骤条、现场反馈、复测验收。 |

完成标准：

```text
点击专家确认后才能生成处置票卡；
点击反馈确认后才能进入报告和案例入库。
```

### 阶段 4：报告、案例和复用

目标：

```text
把第一次闭环沉淀成第二次可复用的知识。
```

页面：

| 页面 | 必做内容 |
| --- | --- |
| 报告和复用职责 | 报告草稿、知识审核、P-1 案例入库、P-2 相似异常命中。 |

完成标准：

```text
P-1 报告未确认、知识审核未通过前，P-2 不应显示命中 P-1 案例；
知识审核通过后，P-2 展示相似标签和复用建议。
```

## 5. 建议数据格式

字段细节、顶层集合、状态枚举和来源字段以 [../../v1/demo-研发基准/05-结构化数据契约.md](../../v1/demo-研发基准/05-结构化数据契约.md) 为唯一事实来源。开发数据包可以从该文档的统一 JSON 样例裁剪，不要在页面代码或开发说明里另造字段。

开发时只需要额外保证两点：

1. 每个页面都读取同一份 demo 数据包。
2. 页面可以解释“运行时从哪里读”和“样例依据来自哪里”。

## 6. 素材准备清单

### P0：没有会影响主线可信度

| 素材 | 用途 |
| --- | --- |
| P1 检测报告抽取结果 | 设备、测点、趋势、频谱、相位、诊断证据。 |
| P1 对中作业卡抽取结果 | 作业卡命中、票卡步骤、许可、工具、验收项。 |
| 阈值和风险等级口径 | 趋势图、关注级事件、诊断解释。 |
| 处置后复测样例 | 现场反馈、闭环成立、报告草稿。 |
| 报告模板 | 报告预览和案例入库。 |

### P1：增强现场感

| 素材 | 用途 |
| --- | --- |
| 点位图和设备图 | 一泵一档、测点高亮、页面真实感。 |
| 历史异常报告 | 历史案例、报告段落、知识库样例。 |
| IMS 单元模型 | 页面字段和设备组织方式。 |
| 维护保养信息表 | 一泵一档和维护记录摘要。 |

### P2：后续加分项

| 素材 | 用途 |
| --- | --- |
| 真实或脱敏 P2 相似案例 | 提升复用验证可信度。 |
| 多故障作业卡 | 二期扩展轴承、不平衡、泄漏等故障。 |
| HSE / 供应链字段样例 | 试点阶段联动展示。 |

## 7. 页面文案原则

1. 说“关注级诊断事件”，不要说“严重事故报警”。
2. 说“疑似不对中”，不要说“系统已自动定责”。
3. 说“专家复核后进入处置”，不要说“AI 自动派工”。
4. 说“对中作业标准模板卡”，不要说“已完成正式生产审批”。
5. 说“演示态处置票卡”，不要说“真实 HSE 办票”。
6. 说“演示构造 / 脱敏样例”，不要把模拟数据讲成真实历史事件。
7. 说“案例复用建议”，不要说“系统自动决定采纳”。

## 8. 分阶段实现目标

| 阶段 | 目标 | 可验收结果 |
| --- | --- | --- |
| 阶段 0：范围冻结 | 冻结 P-1、P-2、5 页路线、数据字段和边界话术。 | 文档和数据包草稿确认。 |
| 阶段 1：页面壳 | 完成 5 页导航和主线状态。 | 可点击走完整体路线。 |
| 阶段 2：证据链 | 完成趋势、频谱、相位、诊断结果展示。 | 疑似不对中证据可解释。 |
| 阶段 3：处置闭环 | 完成专家确认、知识命中、票卡、反馈。 | 从复核到复测能联动。 |
| 阶段 4：报告复用 | 完成报告、案例入库、P-2 复用验证。 | 首次闭环和第二次复用成立。 |
| 阶段 5：彩排交付 | 调整文案、截图、演示脚本和边界说明。 | 8 到 12 分钟稳定演示。 |

## 9. 验收与验证

开发完成前至少验证：

| 验证项 | 方法 |
| --- | --- |
| 文件存在 | 检查 5 页原型和 demo 数据包。 |
| 数据加载 | 页面能读取统一数据包，无空白主流程。 |
| 主线走通 | 从 P-1 异常事件走到 P-2 复用验证。 |
| 状态约束 | 未专家确认不生成票卡，未报告确认不提交入库，未知识审核通过不命中 P-1 案例。 |
| 来源说明 | 页面能解释 `runtime_source` 和 `basis_source`。 |
| 边界文案 | 不出现真实系统接入、真实模型训练、AI 替代专家等误导表述。 |
| 截图验证 | 若是静态 HTML / POC 页面，使用 Playwright 截图验证页面 title、active scene 和错误状态。 |

## 10. 明确不做

```text
不做真实接口接入
不做真实模型训练
不做真实 RAG / 向量库
不做真实大模型 API
不做登录权限审批
不做真实 HSE 办票
不做供应链采购库存联动
不做全故障类型覆盖
不做日常巡检、计划保养、项修、大修完整流程
```
