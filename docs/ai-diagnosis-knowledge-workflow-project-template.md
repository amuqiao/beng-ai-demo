# AI 诊断 + 知识库 + 流程闭环项目骨架

> 本文把一个具体智能诊断演示方案抽象为面向“异常 / 诊断 / 处置闭环”的可复用项目模板，用于快速搭建“发现异常、解释依据、推动处置、沉淀知识、下次复用”的首版 PoC。

---

## 1. 文档职责与不适用范围

### 1.1 本文负责什么

本文负责定义一套可复用的项目骨架，帮助团队在不同业务场景中统一回答：

```text
异常从哪里来
AI 诊断负责判断什么
知识库负责提供什么依据
人工在哪些节点确认
处置流程如何闭环
报告和经验如何沉淀
沉淀后的知识如何被下一次相似事件复用
```

适用读者：

| 读者 | 使用方式 |
|---|---|
| 业务负责人 | 判断首版 PoC 是否讲清业务价值和边界 |
| 产品经理 | 拆分页面、流程节点、人工确认点和资料需求 |
| 解决方案架构师 | 设计模块分层、接口边界和后续替换路径 |
| 开发团队 | 明确首版做什么、不做什么，以及哪些能力先用演示态表达 |
| 知识运营人员 | 准备案例、规则、模板、标签和入库审核机制 |

### 1.2 本文不负责什么

本文不是生产系统实施方案，也不替代具体业务调研。以下内容需要在落地项目中单独设计：

| 不适用范围 | 说明 |
|---|---|
| 具体行业流程规范 | 本文只给通用闭环，不定义任何行业的正式流程制度 |
| 真实模型训练方案 | 本文不规定算法、特征工程、训练集、评测指标和上线门槛 |
| 真实系统集成方案 | 本文不定义具体系统、账号、权限、接口协议或联调计划 |
| 合规审批细则 | 本文只保留人工确认和审核节点，不替代组织内正式审批规则 |
| 全量平台规划 | 本文优先服务首版 PoC，不把所有业务场景一次性展开 |
| 非诊断处置类流程 | 本文不适合直接覆盖纯客服问答、内容生成、搜索门户或无异常闭环的知识管理项目 |

## 2. 整体心智模型

这类项目不要被理解成“一个监控大屏”或“一个 AI 问答窗口”。更准确的心智模型是：

```text
把一次异常事件变成一条可追踪、可解释、可复核、可处置、可沉淀、可复用的闭环。
```

首版 PoC 要证明的不是功能数量，而是闭环是否成立：

```text
能发现：
  异常以事件形式进入系统，而不是散落在报表、截图或人工描述里。

能解释：
  诊断结论必须带证据、阈值、趋势、规则、相似案例或专家经验。

能推动：
  诊断结果能进入处置建议、任务、作业步骤或业务动作。

能把关：
  关键结论、处置决策、报告发布和知识入库必须有人确认。

能沉淀：
  处理过程不只生成一份报告，还要形成结构化案例和可检索标签。

能复用：
  下一次相似事件能命中本次经验，缩短研判和处置路径。
```

### 2.1 三类能力不要混着讲

| 能力 | 负责的问题 | 首版表达方式 |
|---|---|---|
| 诊断能力 | 这是什么异常、风险有多高、依据是什么 | 可用预置规则、样例数据和可解释诊断卡片表达 |
| 知识能力 | 过去有没有类似情况、应该参考哪些规则和案例 | 展示知识命中、引用来源、适用范围和复用标签 |
| 流程能力 | 谁确认、怎么处理、如何反馈、如何归档 | 用状态流转、任务卡、报告草稿和入库审核表达 |

关键边界：

```text
AI 不应凭空替代专业判断。
知识库不应只是资料网盘。
流程闭环不应停在“生成建议”。
人工确认不应被省略。
```

## 3. 通用模块边界

这套骨架的核心不是页面顺序，而是把事实、结论、状态、知识和集成分开。模块可以在首版 PoC 中用同一个服务或同一个前端项目承载，但职责边界应从第一版就写清楚。

```text
业务对象与事实
  -> 证据整理
  -> 诊断编排
  -> 知识检索
  -> 人工决策
  -> 流程闭环
  -> 报告学习
  -> 外部集成
  -> 治理运维
```

| 模块 | 拥有什么 | 不应该做什么 | 首版 PoC 做法 |
|---|---|---|---|
| Object Catalog | 业务对象、对象层级、主数据、标签 | 不做诊断、不推进流程 | 用 1 类对象和少量样例档案 |
| Observation & Evidence | 异常事件、指标、文本、附件、阈值、证据引用 | 不产出正式结论 | 用样例数据形成可回放证据链 |
| Diagnosis Orchestrator | 诊断候选、风险等级、证据标签、建议下一步 | 不直接派工、不自动关单、不写知识库 | 调用规则、样例模型或受控生成输出结构化诊断 |
| Knowledge Service | 案例、规则、标准操作模板、报告模板、专家经验、引用关系、命中原因 | 不决定是否执行处置 | 做可见的知识命中和引用依据 |
| Review & Decision | 人工复核、驳回、覆盖、审批、发布确认 | 不把 AI 建议直接当正式结论 | 保留确认、调整、退回按钮和记录 |
| Workflow / Case Engine | 事件 / 处置生命周期、任务、状态迁移、责任人、SLA、闭环结果 | 不把前端页面步骤当状态机 | 用演示态状态机跑通一条主线 |
| Report & Learning | 报告草稿、案例摘要、复用标签、学习记录 | 不把报告附件当唯一知识源 | 把处理过程转成结构化案例 |
| Integration Contract Layer | 上游数据源、下游系统、模型供应商、通知通道的适配契约 | 不绕过核心模块直接改状态 | 首版用 mock 或导入数据，但先定义契约 |
| Governance & Ops | 配置版本、权限、审计、追踪、模型版本、知识版本、运维查询 | 不等到生产化才补审计口径 | 至少记录配置来源、人工操作和演示数据标识 |

判断一个设计是否可复用，可以先问：

```text
事实由谁拥有？
诊断结论由谁产生？
流程状态由谁推进？
知识依据由谁维护？
外部系统由谁适配？
人工确认在哪里留下记录？
```

如果这些问题回答不清，后续换业务时通常会变成复制一套表和页面，而不是复用项目骨架。

## 4. 核心流程

首版建议只做一条主线，拆成“首次异常闭环”和“相似事件复用”两段。

### 4.1 首次异常闭环

```text
1. 业务对象出现异常
   -> 形成异常事件，展示时间、对象、指标、阈值和状态。

2. 系统整理证据
   -> 展示趋势、指标变化、关联对象、历史记录和事件上下文。

3. 诊断模块输出候选判断
   -> 输出异常类型、风险等级、证据链、置信或评分口径。

4. 知识库命中依据
   -> 命中相似案例、标准操作模板、专家经验、规则条款或报告模板。

5. 人工复核
   -> 专家或责任人确认诊断结论、调整候选原因、决定是否进入处置。

6. 生成处置任务
   -> 生成任务卡、检查项、操作步骤、风险提示、资源需求和验收标准。

7. 执行方反馈
   -> 回填执行过程、处理结果、验证数据、附件和异常说明。

8. 生成报告草稿
   -> 汇总事件、证据、诊断、处置、验证、结论和经验。

9. 审核并沉淀知识
   -> 人工确认报告和案例摘要后，新增结构化案例并更新业务对象履历。
```

### 4.2 相似事件复用

```text
1. 另一条相似异常出现
2. 诊断模块识别相似特征
3. 知识库命中上一次沉淀的案例或预置案例快照
4. 页面展示相似依据、复用建议和适用条件
5. 人工确认是否采纳建议
```

这段复用不需要再做一条完整流程，也不要求证明真实入库后立即被检索引擎命中。首版可以用预置第二事件或预置索引快照表达：

```text
这次沉淀的经验，已经能成为下一次研判和处置的依据。
```

## 5. 可替换业务适配点

这套骨架可以迁移到不同业务领域。迁移时优先替换下列适配点，而不是重写整体流程。

| 适配点 | 需要替换的内容 | 示例占位 |
|---|---|---|
| 业务对象 | 被监测、评估、处置或服务的对象 | 设备、订单、客户、交易、账户、工单、项目 |
| 异常信号 | 触发事件的指标、文本、图像、日志或人工上报 | 指标越限、趋势突变、规则违背、异常描述 |
| 诊断口径 | 从异常到候选原因的判断规则 | 阈值、特征组合、专家规则、分类标签 |
| 知识对象 | 可检索、可引用、可复用的知识资产 | 历史案例、操作模板、规范条款、专家经验 |
| 处置动作 | 诊断后要推动的业务行为 | 检查、修复、审批、联系客户、冻结、复核、补录 |
| 人工角色 | 负责确认、执行、审核、发布的人 | 专家、主管、执行人、审核人、知识管理员 |
| 闭环凭证 | 证明动作完成的记录 | 反馈表、报告、截图、复测数据、签批记录 |
| 复用条件 | 下一次命中经验的相似标准 | 标签、症状、对象类型、风险等级、处置结果 |

适配原则：

```text
先替换业务名词，再确认流程节点。
先确认一条主线，再扩展多场景。
先做可解释闭环，再追求真实模型和真实集成。
配置项要可声明、可读取、可追踪版本，但不等于首版就建设低代码平台。
```

首版配置面可以是静态配置、代码常量、Markdown 表格或种子数据，不要求建设配置后台、低代码平台或通用规则引擎。只有当第二个、第三个业务场景开始复用同一骨架时，再考虑把配置能力产品化。

### 5.1 推荐配置面

| 配置面 | 说明 | 首版最低要求 |
|---|---|---|
| 对象配置 | 对象类型、对象层级、关键字段、展示标签 | 能声明 1 类主对象 |
| 事件配置 | 事件类型、触发来源、风险等级、升级条件 | 能声明 1 类主异常事件 |
| 证据配置 | 指标、文本、附件、阈值、特征标签、可信度 | 能展示证据来源和引用 |
| 诊断配置 | 候选类型、风险等级、建议动作、模型路由 | 能输出结构化诊断卡片 |
| 知识配置 | 案例、规则、标准操作模板、报告模板、引用和适用范围 | 能命中并说明原因 |
| 流程配置 | 节点、状态、角色、人工确认点、SLA | 能跑通一条状态流 |
| 报告配置 | 章节、字段映射、自动生成字段、人工确认字段 | 能生成并审核一份草稿 |
| 集成配置 | 外部字段映射、状态映射、回调、幂等键 | 首版可 mock，但契约要稳定 |

## 6. 模块接口边界

模块边界的目标是防止职责混乱。首版可以是演示态实现，但接口语义应提前稳定。

### 6.0 核心实体归属

核心实体必须有明确的 source of truth。否则实现很容易退化成一个“大事件对象”，把事实、诊断、状态、报告和知识互相覆盖。

| 实体 | source of truth | 可写方 | 版本 / 变更规则 |
|---|---|---|---|
| `object_profile` | Object Catalog | 对象适配器或人工维护入口 | 主数据变更保留更新时间和来源 |
| `event` | Observation & Evidence | 事件接入、人工上报、外部回调适配器 | 原始事件不覆盖，修正应产生修正记录 |
| `evidence` | Observation & Evidence | 数据接入、文档抽取、人工补充 | 证据晚到时追加，不直接改旧诊断结论 |
| `diagnosis` | Diagnosis Orchestrator | 模型、规则、诊断编排器 | 每次诊断生成新版本，记录模型或规则版本 |
| `review_decision` | Review & Decision | 有权限的复核人或审批节点 | 是正式结论生效闸门，不回写覆盖原诊断 |
| `task` | Workflow / Case Engine | 流程引擎或人工派发入口 | 状态迁移必须校验当前状态和幂等键 |
| `report_draft` | Report & Learning | 报告生成器、人工编辑入口 | 草稿可多版，发布版需要审核记录 |
| `knowledge_item` | Knowledge Service | 知识审核入口 | 入库、作废、更新都要保留版本和审核人 |
| `object_history` | Object Catalog 或 Report & Learning | 由闭环完成事件派生写入 | 只记录已审核闭环结果，不记录未确认建议 |

约束口径：

```text
诊断可以建议下一步，但不能直接写 task。
复核可以确认或覆盖诊断，但不能删除原诊断。
流程可以引用知识命中，但不能直接发布知识。
报告可以派生知识草稿，但不能跳过知识审核。
适配器可以转换字段，但不能绕过核心模块直接改状态。
```

### 6.1 异常事件输入

诊断入口应接收结构化事件，而不是只接收一段自然语言。

| 字段 | 含义 |
|---|---|
| `event_id` | 异常事件唯一标识 |
| `object_id` | 业务对象唯一标识 |
| `object_type` | 业务对象类型 |
| `event_time` | 异常发生或被发现时间 |
| `signals` | 触发异常的指标、日志、文本或附件摘要 |
| `thresholds` | 阈值、等级、规则或基线 |
| `context` | 业务对象档案、历史记录、工况或场景上下文 |

### 6.2 诊断模块输出

诊断模块只负责“判断是什么问题以及依据是什么”，不负责直接派发任务或发布正式结论。

| 字段 | 含义 |
|---|---|
| `diagnosis_id` | 诊断结果唯一标识 |
| `event_id` | 关联异常事件 |
| `candidate_type` | 候选异常类型 |
| `risk_level` | 风险等级 |
| `confidence` | 评分或置信口径，首版可标注为演示值 |
| `evidence` | 支撑判断的证据列表 |
| `recommended_next_step` | 建议进入的下一步动作 |
| `requires_human_review` | 是否需要人工复核 |
| `model_or_rule_version` | 模型、规则集或提示词版本 |

诊断失败、证据不足、知识未命中时，应显式返回状态和原因，不要静默降级成默认结论。

### 6.3 人工复核决策

人工复核应形成独立的 `review_decision`，而不是直接改写诊断结果或隐式推进流程状态。

| 字段 | 含义 |
|---|---|
| `decision_id` | 复核决策唯一标识 |
| `diagnosis_id` | 被复核的诊断结果 |
| `diagnosis_version` | 被复核的诊断版本 |
| `reviewer_id` | 复核人或审批节点 |
| `decision` | 通过、调整、驳回、转人工排查等 |
| `approved_candidate_type` | 复核后生效的异常类型或结论 |
| `override_reason` | 调整或驳回原因 |
| `approval_scope` | 本次确认适用的范围，例如仅当前事件或可沉淀为经验 |
| `decided_at` | 复核时间 |
| `audit_note` | 审计备注或引用依据 |

### 6.4 知识检索输出

知识库负责“找依据、给引用、说明适用范围”，不应只返回一段无法追溯的回答。

| 字段 | 含义 |
|---|---|
| `knowledge_hits` | 命中的案例、规则、模板、经验 |
| `source_type` | 知识来源类型 |
| `source_title` | 知识标题 |
| `match_reason` | 为什么命中 |
| `applicability` | 适用条件和不适用条件 |
| `citation` | 可追溯的来源标识 |
| `reuse_tags` | 后续复用标签 |

### 6.5 流程编排输入输出

流程模块负责“谁做、做什么、何时完成、如何验收”。

| 输入 | 输出 |
|---|---|
| 异常事件 | 处置任务 |
| 诊断结果 | 人工复核记录 |
| 知识命中 | 操作步骤和风险提示 |
| 人工确认 | 状态流转和责任人 |
| 执行反馈 | 报告草稿和验收记录 |
| 审核结论 | 知识入库或退回修改 |

流程对象至少应有这些字段：

| 对象 | 最小字段 |
|---|---|
| `task` | `task_id`、`event_id`、`decision_id`、`assignee`、`status`、`idempotency_key`、`created_at`、`updated_at` |
| `execution_feedback` | `feedback_id`、`task_id`、`result`、`evidence_refs`、`submitted_by`、`submitted_at` |
| `report_draft` | `report_id`、`event_id`、`decision_id`、`task_refs`、`version`、`status`、`review_required` |

### 6.6 知识入库边界

入库对象应是结构化经验，而不是简单上传报告附件。

| 入库对象 | 必要字段 |
|---|---|
| 处置案例 | 标题、对象标签、异常标签、触发条件、诊断证据、处置动作、验证结果、适用范围、审核状态 |
| 操作模板 | 适用场景、前置条件、步骤、角色、风险提示、验收标准 |
| 专家规则 | 触发条件、判断逻辑、建议动作、适用边界、维护人 |
| 报告模板 | 章节结构、必填字段、自动生成字段、人工确认字段 |

### 6.7 集成契约边界

外部系统和模型供应商都应通过适配层进入核心流程。适配器只做字段映射、协议转换和状态同步，不应直接修改核心状态。

| 契约项 | 需要定义 |
|---|---|
| 输入契约 | 字段名、类型、必填项、单位、枚举、时间语义 |
| 输出契约 | 响应结构、错误码、异步回调、状态映射 |
| 幂等契约 | 请求唯一键、重复提交返回策略、重放窗口 |
| 版本契约 | schema 版本、兼容策略、废弃策略 |
| 审计契约 | 操作人、来源系统、request_id、trace_id、时间戳 |
| 失败契约 | 可重试错误、不可重试错误、人工处理入口 |

---

## 7. 首版 PoC 范围

首版目标是证明闭环价值，不是证明生产系统已经建成。

### 7.1 建议纳入

| 范围 | 做法 |
|---|---|
| 一条主异常场景 | 选择一个业务最容易确认的典型事件 |
| 一类业务对象 | 聚焦一个对象类型，不做全域对象管理 |
| 一套样例数据 | 使用脱敏数据、模拟数据或业务确认样例 |
| 一个诊断输出卡片 | 展示异常类型、风险等级、证据链和建议动作 |
| 一组知识命中 | 至少包含案例、操作模板、专家经验或规则依据 |
| 一个处置任务流 | 展示复核、任务生成、执行反馈和验收 |
| 一份报告草稿 | 自动汇总过程，但保留人工确认 |
| 一次入库审核 | 演示案例摘要和标签，经人工确认后入库 |
| 一次复用验证（可选增强） | 用预置第二事件或预置索引快照展示相似经验可被复用 |

### 7.2 建议不纳入

| 不做项 | 原因 |
|---|---|
| 多场景并行闭环 | 首版会变大而散，难以验证主线 |
| 真实生产接口联调 | 权限、周期、稳定性和数据安全成本高 |
| 真实模型训练 | 训练数据、评测和上线门槛通常不足 |
| 开放式自由问答 | 容易偏离可控演示和专业边界 |
| 自动发布正式结论 | 关键判断必须保留人工确认 |
| 自动入库正式知识 | 错误知识会放大后续复用风险 |
| 完整移动端或多端体系 | 首版可用响应式页面或样式页表达 |

### 7.3 PoC 验收口径

首版验收不看系统名词堆叠，而看是否能完整走通：

```text
异常事件可见
诊断依据可见
知识引用可见
人工确认可见
处置状态可见
反馈结果可见
报告草稿可见
入库审核可见
相似复用可见（可选增强）
```

如果正在准备首版落地，应先使用第 9 节资料清单确认输入素材，再回到第 8 节评估后续升级。

---

## 8. 后续升级项

PoC 通过后，再按风险和价值逐步替换演示态能力。

| 升级项 | 目标 | 前置条件 |
|---|---|---|
| 真实数据接入 | 从样例数据切换到实时或准实时事件 | 数据权限、字段口径、质量评估 |
| 诊断模型验证 | 用历史样本评估诊断准确率和召回率 | 标注数据、评测集、专家复核机制 |
| 检索引擎落地 | 从预置命中切换到真实检索 | 文档治理、切分策略、索引更新、权限控制 |
| 流程系统集成 | 从演示态状态机切换到真实任务流 | 接口协议、角色权限、异常回滚策略 |
| 知识治理后台 | 支持知识审核、版本、作废、适用范围管理 | 知识责任人、审核制度、生命周期规则 |
| 多场景扩展 | 从一条主线扩展到多类异常和多类处置 | 已验证的主线模板、可复用组件 |
| 指标看板 | 量化节省时间、减少误判、复用次数 | 运行数据、埋点、统计口径 |
| 安全与权限 | 控制数据、知识、结论和操作权限 | 组织角色、审计要求、访问策略 |
| 异步可靠性 | 支持重试、死信、补偿、人工修复 | 幂等键、任务状态、告警和重放工具 |
| 契约治理 | 支持 schema diff、版本兼容和 sunset 策略 | 稳定 API schema、契约测试、调用方清单 |
| 模型治理 | 支持模型版本、评测、回滚和输出追踪 | 样本集、评测指标、版本记录、人工兜底 |

生产化时必须补齐的底线：

```text
关键写操作要有幂等策略。
流程状态要可查询、可审计、可恢复。
知识入库要有审核、版本、作废和引用追踪。
模型输出要记录模型或规则版本。
外部集成失败要显式暴露，不能被默认值吞掉。
权限裁决应在服务端或核心流程层完成，前端只做展示提示。
```

### 8.1 关键失败模式

生产化前至少要明确这些失败模式。PoC 可以先用文档约定和演示数据标注表达，不必一次性建设完整恢复工具。

| 失败模式 | 风险 | 最小恢复口径 |
|---|---|---|
| 新证据晚到 | 旧诊断已经被复核或进入处置，新增证据可能改变结论 | 追加 evidence，生成新 diagnosis 版本，提示是否重新复核 |
| 两人并发复核 | 后提交的复核覆盖先提交的决策 | `review_decision` 写入时校验 diagnosis version 和当前状态 |
| 状态重复推进 | 重复点击、重试或回调导致重复派发任务 | task 状态迁移使用幂等键和当前状态校验 |
| 执行中诊断被覆盖 | 任务执行时诊断结论发生变化 | 标记相关 task 为需确认，禁止自动沿用旧建议 |
| 知识已作废仍被引用 | 复用建议引用过期案例或规则 | knowledge hit 返回知识版本和有效状态，作废知识不得作为默认建议 |
| 模型或规则版本漂移 | 同一事件重跑得到不同结论但无法解释原因 | diagnosis 记录模型、规则或提示词版本 |
| 报告生成成功但入库失败 | 用户以为闭环完成，知识实际未沉淀 | 报告发布和知识入库分状态展示，入库失败进入人工处理 |
| 外部系统部分失败 | 上游事件已进来，下游任务或通知未同步 | 记录集成状态、错误原因和可重放入口 |

## 9. 资料清单

项目启动前应把资料分成“必须提供、必须确认、可代拟后确认”三类。

### 9.1 必须提供的事实资料

| 资料 | 用途 |
|---|---|
| 主业务对象样例 | 决定演示主角、档案页和报告主体 |
| 异常事件样例 | 决定流程起点和事件字段 |
| 指标、日志或描述样例 | 支撑诊断输入和证据展示 |
| 阈值、规则或基线 | 解释为什么触发异常 |
| 历史处理记录 | 支撑案例命中和报告结构 |
| 操作模板或处置规范 | 支撑任务步骤和验收标准 |
| 报告模板 | 支撑报告生成和人工确认字段 |

### 9.2 必须确认的业务口径

| 口径 | 需要确认什么 |
|---|---|
| 主线事件 | 首版只讲哪一类异常 |
| 风险等级 | 等级名称、触发条件、升级条件 |
| 诊断标签 | 候选异常类型如何命名 |
| 人工角色 | 谁复核诊断、谁执行处置、谁审核报告、谁确认入库 |
| 处置边界 | 哪些动作可演示，哪些必须留作扩展 |
| 知识边界 | 哪些材料可作为检索依据，哪些只能作为附件 |
| 入库规则 | 什么内容可以沉淀为正式知识，谁负责审核 |
| 复用条件 | 下一次相似事件按哪些标签或证据命中 |

### 9.3 可代拟后确认的演示资料

| 资料 | 用途 |
|---|---|
| 趋势或事件时间线 | 补齐演示中的异常发展过程 |
| 相似案例摘要 | 支撑知识命中页面 |
| 专家经验短规则 | 支撑可解释建议 |
| 处置反馈样例 | 支撑闭环完成和报告生成 |
| 新增案例摘要 | 支撑知识入库演示 |
| 第二次相似事件 | 支撑可选复用验证 |

## 10. 复用检查清单

在把本模板迁移到新业务场景前，用以下清单做一次收口。

### 10.1 边界检查

| 检查项 | 是否通过 |
|---|---|
| 文档和方案没有绑定具体行业名词、系统名词或组织名词 |  |
| 首版只选了一条主线，没有把所有场景一次性展开 |  |
| 已明确哪些能力是演示态，哪些能力是后续真实接入 |  |
| 已保留关键人工确认节点 |  |
| 未宣称 AI 自动替代专家或责任人发布正式结论 |  |

### 10.2 闭环检查

| 检查项 | 是否通过 |
|---|---|
| 异常事件有明确来源和字段 |  |
| 诊断输出有证据链和风险等级 |  |
| 知识命中能说明来源、适用条件和命中原因 |  |
| 处置任务能说明责任人、步骤、验收和反馈字段 |  |
| 报告草稿能汇总事件、诊断、处置和验证结果 |  |
| 知识入库不是简单保存附件，而是形成结构化案例 |  |
| 复用验证能展示相似经验可被再次引用，不要求真实入库后即时检索 |  |

### 10.3 资料检查

| 检查项 | 是否通过 |
|---|---|
| 已拿到或构造主业务对象样例 |  |
| 已拿到或构造异常事件样例 |  |
| 已确认阈值、规则或风险等级口径 |  |
| 已准备至少 2-3 条相似案例或专家经验 |  |
| 已准备至少 1 份操作模板或处置规范 |  |
| 已准备报告模板或报告章节结构 |  |
| 已准备第二次相似事件用于可选复用演示 |  |

### 10.4 接口检查

| 检查项 | 是否通过 |
|---|---|
| 异常事件、诊断结果、知识命中、处置任务、入库案例的字段已定义 |  |
| 模块之间没有互相越权，例如诊断模块直接派工或知识库直接发布结论 |  |
| 演示态数据和真实生产数据有清晰标注 |  |
| 后续替换真实模型、真实检索、真实流程系统时不需要推翻页面主线 |  |

### 10.5 生产化边界检查

| 检查项 | 是否通过 |
|---|---|
| 关键操作已设计幂等键和重复提交处理口径 |  |
| 流程状态、人工操作、模型版本和知识版本可审计 |  |
| 外部集成失败不会被静默吞掉，有人工处理入口 |  |
| 知识入库有审核、作废、更新和引用追踪策略 |  |
| API 或数据契约有版本策略，破坏性变更可被识别 |  |
| 权限边界不依赖前端隐藏按钮或页面路由 |  |

## 11. 一句话复用口径

对外介绍时，可以把这套骨架压缩为：

```text
先用一条典型异常证明闭环：AI 负责辅助诊断和成文，知识库负责提供依据和复用经验，流程系统负责承载确认、处置、反馈和入库；首版先演示可解释、可确认、可沉淀、可复用，后续再替换真实模型、真实检索和真实系统接口。
```
