# 输油泵智能运维助手（"泵智护"）demo 业务讨论简版

> 文档性质：业务沟通稿 / 会前讨论稿
> 适用场景：用于和业务方确认 demo 方向、演示主线、资料准备和首版边界
> 不适用：本文不是技术详设、不是报价单、不是最终验收文件

---

## 1. 我们对材料的理解

根据《输油泵智能运维助手申报书》及参赛材料，我们的初步判断是：本次 demo 适合围绕全集团输油泵智能运维，先形成一个可演示、可汇报、可继续扩展的业务闭环，用于说明"泵智护"不是单纯监测看板，而是可以支撑输油泵从预警到处置再到知识沉淀的智能运维助手。

材料中反复出现的核心背景是：

| 业务背景 | 材料表述 |
|---|---|
| 管理对象规模大 | 全集团在役主泵 1558 台 |
| 监测基础已有但覆盖不足 | 已接入频谱分析数据 128 台，接入率 8.2% |
| 运维痛点明确 | 历史故障数据库缺失、周期性维护为主、IMS 承载不足、专家能力分布不均 |
| 希望形成智能闭环 | 预警、诊断、排查、工单、报告、知识库回流 |
| demo 条件有锚点 | 材料写到可基于集团通用模拟数据集完整演示全业务流程 |

我们的理解是：这次 demo 的重点不是一次性做完所有正式系统能力，而是让评委或领导看懂并相信：

```text
输油泵出现异常趋势
  -> 系统能提前发现
  -> 数智员工能辅助分析和排查
  -> 专家能复核确认
  -> 作业处置能流转
  -> 报告和知识能沉淀
  -> 后续可逐步接入真实系统和更多设备
```

## 2. 建议的 demo 定位

【建议】首版 demo 定位为"可交互模拟 PoC"。

这意味着：

- 不是静态 PPT，也不是只点页面的原型；
- 可以现场走通一条完整业务流程；
- 关键业务动作可交互、可展示、可解释；
- 数据可先采用演示数据或脱敏样例；
- 后续正式项目可逐步替换为真实系统和真实数据。

不建议首版直接定位为"真实系统集成 demo"或"试点 MVP"。这两类形态会提前引入接口权限、生产环境、联调窗口、数据合规、现场网络等问题，容易把大赛/汇报 demo 拉成正式项目建设。

## 3. 推荐演示主线

【建议】首版只做一条主线，把它做顺、做深、做可信。

推荐主线：

```text
一台输油泵出现早期异常趋势
  -> 监视中心收到预警
  -> 数智员工关联历史案例并给出排查方向
  -> 专家查看分析结果并复核
  -> 演示作业建议、工单和备件需求生成过程
  -> 作业区人员在移动端样式页模拟反馈
  -> 生成异常事件分析示例报告
  -> 演示报告和处置经验回流知识库 / 一机一档
```

这个主线能对应材料里的三个关键表达：

| 材料目标 | demo 中如何体现 |
|---|---|
| 可执行 | 从预警到工单、作业反馈、报告发布形成闭环 |
| 可决策 | 通过趋势、频谱、多参数和案例关联说明为什么预警、为什么这样处置 |
| 可进化 | 处置完成后形成报告、案例和知识沉淀 |

## 4. 首版建议展示内容

| 模块 | 业务方能看到什么 | 首版建议 |
|---|---|---|
| 全局态势 | 1558 台主泵、128 台已接入、接入率 8.2%、设备健康概览 | 用材料指标做首页认知入口 |
| 早期预警 | 某台输油泵出现异常趋势，展示提前预警过程 | 用时间轴回放表达"提前发现" |
| 智能诊断 | 展示疑似故障、关联案例、排查方向 | 让数智员工承担辅助分析角色 |
| 专家复核 | 专家查看诊断依据并确认结论 | 保留专家把关，增强可信度 |
| 处置流转 | 作业卡、工单、备件、票证、异常事件状态的演示联动 | 体现跨系统协同效果 |
| 移动端反馈 | 作业区人员查看任务并模拟提交处理结果 | 用移动端页面展示现场闭环 |
| 报告生成 | 生成异常事件分析报告 / 优化建议报告示例 | 作为演示高潮 |
| 知识沉淀 | 展示案例库、知识库、一机一档的回流效果 | 体现可进化 |

## 5. AI 与数智员工的建议口径

材料中提到 WeAgent、数智员工、AI 原生载体、知识库等内容。首版 demo 中建议把 AI 设计成"辅助业务闭环"而不是"替代专家决策"。

【建议】首版 AI / 数智员工承担三类角色：

| 角色 | 展示方式 |
|---|---|
| 辅助分析 | 根据预警信息、历史案例和设备状态给出疑似原因 |
| 引导排查 | 按业务流程提示下一步检查项、作业卡和处置建议 |
| 辅助成文 | 根据处置过程生成报告初稿，专家确认后发布 |

【建议】最终诊断和报告发布仍保留专家确认环节。这样既能体现智能化价值，也更符合设备运维场景的责任边界。

## 6. 首版需要业务方确认的问题

为保证 demo 能按目标落地，建议会前或会上先确认以下问题：

| 编号 | 需要确认 | 建议讨论方向 |
|---|---|---|
| Q1 | demo 主要观众是谁？大赛评委、集团领导，还是业务专家？ | 以大赛/领导汇报为主，兼顾专家追问 |
| Q2 | 演示时长大概多久？ | 建议控制在 8-12 分钟 |
| Q3 | 主线故障选哪一类？ | 建议先选轴承故障或不对中故障之一 |
| Q4 | 是否能提供通用模拟数据集或脱敏样例？ | 优先使用业务方已有数据 |
| Q5 | 是否能提供 5-10 条典型故障案例？ | 用于增强诊断和知识库可信度 |
| Q6 | 作业卡、工单、报告模板是否能提供脱敏样例？ | 建议由业务方提供真实模板 |
| Q7 | demo 现场演示环境是什么？ | 确认内网现场演示、外网演示、离线演示或录屏备份 |
| Q8 | 是否需要同时呈现 PC 大屏、专家端和移动端效果？ | 明确现场展示设备和切换方式 |
| Q9 | 本次 demo 是否需要体现与集团数智员工底座 / IMS 平台的关系？ | 确认体现到"架构说明"、"界面标识"还是"实际接入" |
| Q10 | 是否接受首版使用演示数据完整展示流程？ | 结合材料中的模拟数据演示依据共同确认 |
| Q11 | 讨论口径是否以"主线演示完整 + 关键节点可查看"为准？ | 会前共同确认 |

## 7. 首版建议边界

为了保证 demo 在大赛或汇报前可控落地，建议首版先聚焦"一条完整闭环"，以下内容作为后续正式项目或增强项讨论：

| 后续增强项 | 建议原因 |
|---|---|
| 真实生产系统接口全面打通 | 涉及权限、测试环境、联调和数据安全，适合正式项目阶段 |
| 深度模型训练与准确率验证 | 需要历史故障样本、标签和专家评测集 |
| 原生 App | 首版用移动端页面即可说明作业区闭环 |
| 知识图谱引擎 | 首版先证明知识沉淀，图谱化可后续建设 |
| 无线传感器 / 硬件接入 | 属于现场试点范围 |
| 多条故障主线 | 第一条主线稳定后再扩展 |

这里不是否定这些能力，而是建议按阶段推进：先用 demo 证明业务闭环成立，再进入真实系统接入、模型训练、试点推广。

## 8. 建议的会议结论

建议本次需求讨论会最终形成以下结论：

```text
1. demo 首版形态：可交互模拟 PoC。
2. demo 主线：一台输油泵从早期预警到知识沉淀的完整闭环。
3. demo 重点：证明可执行、可决策、可进化。
4. 数据原则：优先使用业务方通用模拟数据集或脱敏样例。
5. AI 口径：数智员工辅助分析、引导排查、生成报告示例，专家最终确认。
6. 首版边界：先做一条主线，不把真实系统全面接入和模型训练作为首版前提。
7. 下一步动作：业务方确认主线故障、数据样例、模板样例、演示环境和验收口径。
```
