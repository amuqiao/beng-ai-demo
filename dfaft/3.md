有必要，而且这是 **demo 开工前必须拍板的工程决策**。

你现在缺的不是“业务故事线”，而是一个更直接的 **demo 工程决策模型**。它要回答：

```text
这个 demo 到底做到什么真实程度？
哪些只是演示？
哪些需要真实接入？
哪些一旦选择就会影响工期、报价、风险？
```

可以给业务方一个精简版决策结构，不暴露你的内部实现细节，但让他们知道每个选择的后果。

```text
demo 工程决策模型

一、demo 形态决策
────────────────
A. 页面交互演示
  做法：
    页面可点击，流程可走通，数据为预置演示数据
  适合：
    领导汇报、方案初审、时间紧
  风险：
    专家追问时技术可信度较弱

B. 可交互模拟 PoC【建议】
  做法：
    页面可交互，关键分析过程有演示逻辑，数据用模拟/脱敏样例
  适合：
    大赛演示、立项汇报、业务验证
  优点：
    能讲清闭环，也能控制范围
  风险：
    需要业务方提供样例数据和模板

C. 半真实集成 demo
  做法：
    部分接入真实系统或真实模型能力
  适合：
    已有测试环境、接口、账号、数据权限
  风险：
    联调周期和现场稳定性不可控

D. 试点 MVP
  做法：
    进入真实业务环境，接真实数据和真实流程
  适合：
    正式项目一期
  风险：
    已经不是 demo 范围


二、AI / 大模型决策
────────────────
A. 仅页面交互，不接大模型
  展示方式：
    数智员工话术、排查建议、报告内容为预置内容
  优点：
    稳定、可控、成本低
  不足：
    AI 真实感弱
  适合：
    纯领导汇报型 demo

B. 接入大模型 API【建议，如环境允许】
  展示方式：
    数智员工可生成排查解释、报告初稿、问答回复
  优点：
    AI 感更真实，演示效果更好
  前提：
    允许外部 API 或集团模型 API
    演示现场网络可用
    数据脱敏合规
  风险：
    输出稳定性、网络、账号、调用额度需要控制

C. 接集团私有化大模型 / 数智员工底座
  展示方式：
    使用集团已有模型或数智员工能力
  优点：
    更符合材料里的“私有化底座”“数智员工”表述
  前提：
    业务方提供底座通道、账号、权限、调用方式
  风险：
    联调和内网环境会增加周期

D. 本地化部署大模型
  展示方式：
    demo 自带本地模型环境
  优点：
    不依赖外网
  不建议首版：
    成本高、部署重、现场机器要求高
  适合：
    明确要求离线且无集团底座可用时


三、智能体 / 数智员工决策
────────────────
A. 预置流程式数智员工【建议基线】
  做法：
    按预警、排查、工单、报告流程引导
  优点：
    现场稳定，边界清楚
  适合：
    首版 demo

B. 限定意图 + 大模型生成
  做法：
    固定业务范围内支持问答和报告生成
  优点：
    兼顾 AI 感和可控性
  前提：
    需要确认模型接口和知识材料

C. 开放式 Agent
  做法：
    让智能体自主理解问题、调用工具、生成流程
  不建议首版：
    现场不可控，验收边界不清


四、数据决策
────────────────
A. 全部演示数据【建议基线】
  内容：
    设备台账、趋势、频谱、工单、报告、知识库均用演示数据
  优点：
    稳定、可控、适合大赛现场
  依据：
    材料中已有“通用模拟数据集可完整演示”表述

B. 脱敏真实样例
  内容：
    使用 1-2 台设备的脱敏波形、频谱、维修案例
  优点：
    可信度更高
  前提：
    业务方提供样例并确认可用于演示

C. 真实系统实时数据
  内容：
    接入监测平台、IMS、PI 等真实系统
  不建议首版：
    权限、网络、接口、稳定性、合规风险较高


五、时序数据决策
────────────────
A. 演示级时序样例【建议】
  做法：
    构造 72 小时趋势曲线和预警时间轴
  适合：
    展示提前预警和趋势分析

B. 脱敏真实时序片段
  做法：
    使用业务方提供的历史片段
  优点：
    更可信
  前提：
    需要字段、单位、采样频率、时间范围

C. 正式时序平台
  不建议首版：
    涉及采集、存储、数据质量、性能和治理
  适合：
    正式项目阶段


六、视觉模型决策
────────────────
A. 不做视觉模型【建议】
  原因：
    材料未提图像、视频、摄像头、YOLO
    输油泵主线是振动、频谱、工艺参数和案例诊断

B. 新增视觉识别
  只有在业务方新增明确场景时考虑：
    仪表识别
    现场跑冒滴漏识别
    作业行为识别
  影响：
    需要图像样本、摄像头、标注、模型训练
    会明显扩大范围


七、系统接口决策
────────────────
A. Mock / 演示数据接口【建议基线】
  做法：
    模拟智能监测平台、IMS、PI、供应链、HSE、PPS 数据
  优点：
    可稳定演示完整闭环

B. 只读接入部分真实系统
  前提：
    有测试环境、账号、接口文档、网络权限
  风险：
    联调周期增加

C. 写入真实系统
  不建议 demo 阶段：
    涉及生产责任、审批、审计、安全


八、移动端决策
────────────────
A. 移动端样式页面【建议】
  做法：
    在 Web 中展示作业区人员接收任务和反馈
  优点：
    足够表达现场闭环

B. 原生 App
  不建议首版：
    开发、安装、测试成本高
  只有在必须真机安装时考虑


九、推荐首版组合
────────────────
建议首版选择：

  demo 形态：
    可交互模拟 PoC

  AI：
    预置流程式数智员工
    + 可选大模型 API 生成报告/解释
    + 专家最终确认

  数据：
    演示数据
    + 尽量使用脱敏真实样例增强可信度

  时序：
    72 小时趋势回放

  系统：
    演示数据接口，不接生产系统

  移动端：
    移动端样式页面

  视觉：
    不做 YOLO / 视觉模型

  大模型部署：
    优先确认是否可用集团底座
    无底座则评估外部 API
    不建议首版本地化部署


十、需要业务方拍板
────────────────
请业务方确认：

  1. demo 是领导汇报、大赛演示，还是专家评审？
  2. 是否接受“可交互模拟 PoC”作为首版形态？
  3. 是否必须真实调用大模型？
  4. 是否必须接集团私有化大模型 / 数智员工底座？
  5. 是否允许使用外部大模型 API？
  6. 是否必须离线或内网演示？
  7. 是否能提供脱敏数据样例？
  8. 是否必须接真实 IMS / PI / 监测平台？
  9. 是否需要原生 App？
  10. 是否确认首版不做视觉模型 / YOLO？
```

我建议你把这个作为 **“demo 工程决策页”** 加到业务讨论材料里。

它的价值是：

```text
业务方能看到：
  我们不是只会做页面
  我们知道 demo 有不同真实程度
  我们知道哪些选择会影响落地

你自己能控制：
  不默认接大模型
  不默认本地部署
  不默认真实系统集成
  不默认视觉模型
  不默认原生 App
  不默认正式项目范围
```

最关键的一句话可以这样说：

> 首版 demo 建议按“可交互模拟 PoC”推进；大模型接口、集团底座、真实系统接入、本地化部署、视觉模型等都作为工程决策项逐项确认，不默认纳入首版范围。
