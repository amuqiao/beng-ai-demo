# 输油泵智能运维助手（"泵智护"）demo 主线骨架与工程决策讨论稿

> 文档性质：业务讨论稿 / demo 会前对齐材料
> 面向读者：业务方、汇报牵头人、技术方案沟通人员
> 使用方式：先对齐 demo 怎么演，再确认工程实现深度
> 不适用：本文不是技术详设、不是报价单、不是最终验收标准

---

## 1. 一句话目标

本次 demo 建议先证明一件事：

```text
一台输油泵从早期异常到闭环处置，
可以通过“预警、诊断、复核、处置、报告、知识沉淀”
形成一条可演示、可解释、可继续扩展的智能运维闭环。
```

首版不建议先做成“大而全平台”，而是先把一条主线演顺、演可信；真实系统接入、更多设备、更多故障类型和正式项目建设，可作为后续升级方向讨论。

## 2. demo 主线骨架

```text
入口：设备态势
  展示 1558 台主泵、128 台已接入、8.2% 接入率等材料指标
      │
      ▼
事件：一台输油泵出现异常趋势
  振动 / 温度 / 压力 / 电流等参数出现异常变化
      │
      ▼
预警：系统提示早期风险
  用 72 小时时间轴回放，说明风险不是故障后才发现
      │
      ▼
诊断：数智员工辅助分析
  关联历史案例、设备履历、参数趋势，给出疑似原因和排查方向
      │
      ▼
复核：专家确认判断
  专家查看趋势、频谱、案例、建议，确认故障类型和处置方向
      │
      ▼
处置：作业流程演示
  演示作业卡、工单、备件需求、票证、异常事件记录样例的协同过程
      │
      ▼
反馈：作业区模拟闭环
  移动端样式页展示任务接收、执行反馈和结果记录
      │
      ▼
报告：生成事件分析示例
  形成故障原因、排查过程、处置措施、后续建议
      │
      ▼
沉淀：知识回流
  展示案例库 / 知识库 / 一机一档的新增效果
```

这条主线对应材料中的三个目标：

| 目标 | demo 里证明什么 |
|---|---|
| 可执行 | 预警不是孤立告警，可以推动处置流程 |
| 可决策 | 诊断不是一句结论，有趋势、参数、案例和专家复核依据 |
| 可进化 | 处置结果不是一次性记录，可以沉淀为案例和知识 |

## 3. 业务痛点示例与演示设计

### 痛点 1：异常发现偏晚

```text
现状痛点：
  传统监测更偏单点告警，
  容易等到振动、温度等指标明显异常后才处理。

demo 怎么演：
  选一台主角泵，
  展示 72 小时时间轴趋势：
    正常期
      -> 轻微异常期
      -> 预警触发
      -> 风险升级

观众看到：
  趋势曲线逐步劣化，
  系统在故障扩大前提示风险。

证明价值：
  demo 能说明“提前发现、提前研判、提前组织处置”的价值。
```

### 痛点 2：诊断依赖专家经验

```text
现状痛点：
  故障判断依赖专家经验，
  一线人员难以快速形成排查方向。

demo 怎么演：
  数智员工根据预警信息关联：
    设备履历
    历史故障案例
    参数趋势
    频谱/波形样例

  给出：
    疑似故障类型
    相似案例
    排查步骤
    专家复核入口

观众看到：
  系统不是只弹一个告警，
  而是给出“为什么怀疑、怎么排查、谁来确认”。

证明价值：
  经验可以被沉淀、复用，并辅助一线快速判断。
```

### 痛点 3：处置流程分散

```text
现状痛点：
  预警、工单、备件、票证、异常事件、现场反馈分散在不同系统或流程中，
  管理人员难以一眼看到处置进展。

demo 怎么演：
  从专家确认后进入处置流程：
    调取作业卡
      -> 生成工单示例
      -> 展示备件需求
      -> 展示 HSE 票证关联
      -> 展示 PPS 异常事件记录
      -> 作业区移动端反馈

观众看到：
  一次预警可以串起后续处置动作，
  每个环节都有状态和记录。

证明价值：
  demo 能说明“预警到闭环”的流程价值，而不是只做监测页面。
```

### 痛点 4：报告和知识沉淀靠人工

```text
现状痛点：
  故障排查过程、维修记录、处置经验需要人工整理，
  经验容易停留在个人或单次事件中。

demo 怎么演：
  处置完成后生成一份异常事件分析示例报告：
    事件概况
    异常趋势
    疑似原因
    排查过程
    处置措施
    后续建议

  报告发布后演示：
    案例库新增效果
    知识库新增效果
    一机一档履历更新样例

观众看到：
  一次故障处置可以变成可复用知识。

证明价值：
  demo 能体现“可进化”，为后续集团范围经验复用打基础。
```

## 4. 演示页面顺序

```text
P1 首页态势
  1558 台主泵 / 128 台已接入 / 8.2% 接入率 / 健康概览

P2 设备详情
  主角泵档案、运行状态、历史记录、当前风险

P3 预警时间轴
  72 小时趋势回放，展示异常如何逐步出现

P4 智能诊断
  参数趋势、频谱/波形样例、相似案例、疑似原因

P5 数智员工排查
  排查步骤、作业建议、专家复核入口

P6 专家复核
  专家查看依据并确认处置方向

P7 作业处置
  作业卡、工单、备件需求、票证、异常事件记录样例的演示联动

P8 移动端反馈
  作业区人员查看任务并模拟提交处理结果

P9 报告生成
  异常事件分析报告 / 优化建议报告示例

P10 知识回流
  案例库、知识库、一机一档新增效果
```

## 5. 工程决策总览

本节不是技术详设，而是需要业务方理解和拍板的 demo 真实程度选择。

```text
demo 真实程度由 7 类决策共同决定：

  demo 形态
    页面原型 / 可交互模拟 PoC / 半真实集成

  数据来源
    示例数据 / 脱敏真实样例 / 真实系统数据

  AI 能力
    模板驱动示例 / 真实 AI 生成

  数智员工
    流程式引导 / 限定问答 / 开放问答式助手

  模型来源与部署
    不接模型 / 调用可用模型通道 / 接集团底座 / 本地部署

  系统接口
    演示数据 / 只读接入 / 写入真实系统

  时序数据
    72 小时趋势样例 / 脱敏真实片段 / 正式时序平台

  移动端与视觉
    移动端样式页 / 原生 App / 视觉模型
```

## 6. 工程决策表

| 决策项 | 选项 A | 选项 B【建议首版】 | 选项 C | 需要业务方确认 |
|---|---|---|---|---|
| demo 形态 | 页面交互原型 | 可交互模拟 PoC | 半真实集成 / 试点 MVP | 本次是汇报演示、比赛演示，还是试点验证 |
| 数据来源 | 全部预置示例 | 演示数据 + 脱敏样例 | 真实系统实时数据 | 是否有通用模拟数据集、脱敏波形、案例和模板 |
| AI 是否真实参与演示 | 模板驱动示例，不真实调用模型 | 可选真实 AI 生成报告/解释 | AI 参与有限问答 | 是否必须真实调用模型能力 |
| 模型来源与部署约束 | 不接模型 | 调用可用模型通道 | 接集团底座 / 本地部署 | 是否允许外部 API、是否必须内网、是否有集团底座通道 |
| 数智员工 | 流程式引导 | 限定业务范围内辅助分析和排查 | 开放问答式助手 | 是否需要体现集团数智员工底座，体现到什么程度 |
| 系统接口 | 全部演示数据 | 演示数据模拟系统关系 | 真实接入 IMS / PI / 监测平台等 | 是否有测试环境、账号、接口权限和联调窗口 |
| 时序数据 | 静态截图 | 72 小时趋势回放和参数曲线 | 正式时序平台 | 是否提供 PI 字段、采样频率、单位和脱敏片段 |
| 移动端 | 不展示移动端 | 移动端样式页 | 原生 App | 是否必须真机安装和现场操作 |
| 视觉模型 | 不涉及 | 首版不做 | 新增视觉识别模型 | 是否存在图像、视频、摄像头类业务场景 |

## 7. 推荐首版组合

```text
推荐首版：
  可交互模拟 PoC

数据：
  演示数据为主，
  尽量叠加少量脱敏真实样例增强可信度。

AI：
  数智员工以辅助分析、引导排查、报告示例生成为主。
  是否真实调用 AI API 作为单独确认项。

系统：
  首版展示 IMS、PI、供应链、HSE、PPS 等系统关系，
  不把真实生产系统全面接入作为前提。

时序：
  做 72 小时趋势回放和关键参数曲线，
  不先建设正式时序平台。

移动端：
  做移动端样式页展示作业区闭环，
  不默认开发原生 App。

视觉：
  材料未体现图像/视频场景，
  首版不建议加入视觉识别模型。
```

## 8. AI 接口与部署方式怎么讨论

```text
如果只是汇报型 demo：
  可以不真实调用大模型，
  用模板驱动示例和报告样例提升现场稳定性。

如果需要体现 AI 真实感：
  可考虑调用 AI API，
  用于排查解释、报告示例生成、有限问答。

如果必须符合集团私有化路线：
  需要确认集团数智员工底座 / 私有化模型是否能提供 demo 通道。

如果必须离线且不能用集团底座：
  才讨论本地化部署模型。
  这会显著增加部署、算力、调试和现场保障工作。
```

建议会上的确认口径：

```text
AI 是否真实调用，不影响主线闭环设计；
但会影响 demo 的真实程度、现场环境、数据合规和实施周期。
```

## 9. 需要业务方拍板的问题

| 编号 | 问题 | 建议讨论方向 |

| Q1 | demo 主要面向谁？ | 大赛评委 / 集团领导 / 业务专家 |

| Q7 | 是否必须接集团数智员工底座？ | 确认体现方式：架构说明 / 界面标识 / 实际接入 |

| Q9 | 是否必须内网或离线演示？ | 决定 AI、部署和现场备份方案 |
| Q10 | 是否需要原生 App？ | 首版建议移动端样式页 |
| Q11 | 是否需要视觉模型？ | 材料未体现图像/视频场景，首版建议不做 |

## 10. 会上可直接使用的收口话术

```text
建议首版 demo 不先做成完整平台，
而是围绕一台输油泵，把“预警、诊断、复核、处置、报告、知识沉淀”
这一条闭环演完整。

工程上建议按“可交互模拟 PoC”推进：
  数据以演示数据和脱敏样例为主；
  AI 是否真实调用单独确认；
  系统接口先展示关系，不默认接生产系统；
  时序先做 72 小时趋势回放；
  移动端先做样式页；
  视觉识别模型材料未体现，首版不纳入。

这样既能体现材料中的数智员工、知识库、跨系统协同价值，
也能把 demo 范围、现场稳定性和后续正式项目边界控制住。
```
